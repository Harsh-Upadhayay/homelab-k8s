# v4.0 — Developer Workspace (ADR-0054 … ADR-0066)

> Back to [[Homelab Learning Map]] · Previous [[v2.0 - Operability]] · Index [[README|ADR index]]

Every milestone up to here treated the cluster as somewhere to *run* things and the MacBook as where they get *written*. This one moves the writing across the wire too. Development leaves the laptop entirely: the devbox pod holds the checkout, the language server, the dependency caches, the compilers and the test runs, and the Mac becomes a thin client — no container runtime, no language server, no local builds, nothing but a terminal and VS Code's Remote-SSH front half. The win is concrete and measurable in battery: the single largest sustained consumer during a normal working day is a language server indexing a repo, and that process now runs on hardware that is plugged into a wall.

Two Kubernetes facts, neither of them negotiable, did most of the architectural work here. **PVCs are namespaced** — a volume cannot be mounted from a namespace it does not live in — which is what collapses the natural "one namespace per project" instinct into a single flat `workbench` namespace (ADR-0054), because the alternative is either a devbox per project or a shared RWX volume, and RWX is separately rejected on performance grounds (ADR-0055). **containerd reads images only from its own per-node content store** — an image sitting on a PVC is invisible to the kubelet no matter how the manifest is written — which is why an in-cluster registry is a hard requirement rather than a nicety (ADR-0059). Everything else in this log follows from those two constraints plus one policy line: no external credential ever enters this cluster.

That policy line is what makes the git story interesting. The Mac already legitimately holds a GitHub credential; the cluster does not and will not. Git will run its wire protocol over any transport that carries stdin and stdout, and `kubectl exec` is one, so code moves by pushing a pack file down an exec pipe rather than by giving the cluster a PAT or a deploy key (ADR-0056). A compromised devbox cannot pull, push, or even enumerate an org, because there is nothing there to do it with.

The remaining decisions are mostly about *not* building things. No Makefile target vocabulary, because the abstraction only ever existed to feed a remote-exec transport that SSH made unnecessary (ADR-0057). No image rebuild in the inner loop, because source and dependency directories both live on the PVC (ADR-0058). No CI role for the in-cluster builder, ever, because artifacts that Argo CD deploys must be reproducible from git (ADR-0060). No auto-sync or self-heal on the `workbench` Application, because a dev namespace is poked at imperatively by design and Argo would spend its day undoing that (ADR-0061). No in-cluster development of `homelab-k8s` or `homelab` at all, because a `terraform apply` running on the cluster it provisions can delete its own execution environment mid-apply (ADR-0062). And no backups of the workspace volume — stated as a decision rather than left as a gap, because GitHub is the real backup and the operational rule is *commit before you stop* (ADR-0063). The one thing genuinely added rather than declined is the access path: real Tailscale SSH, with no sshd, no host keys, and no `authorized_keys` file anywhere (ADR-0064) — run inside the devbox container rather than the sidecar originally specified, because Tailscale SSH spawns the login shell in the filesystem of whichever container runs `tailscaled`. The devbox's own Kubernetes access is namespace-admin scoped to `workbench` by a `RoleBinding` referencing the built-in `admin` `ClusterRole` (ADR-0065).

## ADR-0054 — One flat `workbench` namespace holding the devbox and every project's app containers
**Status:** Accepted — namespace and PVC live and verified (2026-07-29); devbox tooling still open (issue #59)

**Context:** The instinct was one namespace per project — `kiroku`, `ai-scraping`, and so on — matching how the platform already separates operators (ADR-0045's one-namespace-per-operator pattern) and how every Kubernetes tutorial models multi-tenancy. That instinct dies on a single fact: **PersistentVolumeClaims are namespaced objects**, and a pod can only mount a PVC that lives in its own namespace. The whole premise of this milestone is one workspace volume holding all 14 repos plus their dependency directories, mounted simultaneously by the devbox (where code is edited) and by each project's app containers (where it runs, per ADR-0058). Per-project namespaces therefore force one of exactly two things: a separate devbox pod per namespace, each with its own PVC — which multiplies the workspace, the tool installs, the VS Code server, and the storage footprint by the project count and destroys the "one shell, all my code" property that motivated the design — or a single ReadWriteMany volume shared across namespaces, which ADR-0055 rejects independently on performance.

**Decision:** A single `workbench` namespace holds the devbox pod and every project's app containers together. One PVC, one devbox, one flat pool of Deployments and Services.

> **Amendment (2026-07-28, pre-implementation).** The original text placed this namespace "under the existing `personal` AppProject," labeled `group: personal`. Both are wrong, for the reasons set out in the ADR-0061 amendment: the `personal` project is the fence for **code arriving from external repos**, and workbench has no external repo — every manifest lives in this one. Workbench is treated as a **platform component**: manifests at top-level `k8s/workbench/manifests/` under the `default` project, matching `k8s/longhorn/`, `k8s/traefik/`, and every other platform component. The `group: personal` label is dropped; that label is the `k8s/apps/` grouping convention and does not apply here.

Project separation is expressed by naming convention rather than by namespace boundary: service names are project-prefixed (`kiroku-api`, `kiroku-postgres`, never bare `api`/`postgres`). Dev hostnames are also disambiguated against live workloads — `kiroku` already runs in-cluster, so its dev exposure is `kiroku-dev`.

> **Amendment (2026-07-28, pre-implementation) — the port-block scheme is dropped.** The original text allocated dev-server ports "in per-project blocks recorded in a table (kiroku 5173–5179, ai_scraping 5180–5189, …) so several dev servers coexist without collision," and the ROADMAP justified it as necessary "since a flat namespace has no other separation." **That rationale is wrong on the mechanism.** A port lives in a network namespace, and in Kubernetes the *pod* is the network namespace: every pod gets its own IP and its own full port space. A flat Kubernetes namespace does not cause port collisions, and per-project namespaces would not have prevented any.
>
> Working the four real cases: two app-container pods both binding 5173 — **no collision** (separate pods). Two Tailscale `Ingress` frontends on 5173 — **no collision** (separate tailnet nodes). Two dev servers in two tmux panes *inside the devbox pod* — **collision**, since they share one pod's network namespace. Two `kubectl port-forward` sessions on the Mac — **collision**, in the Mac's local port space.
>
> Only the last two collide, and neither justifies pre-allocation. The devbox case announces itself instantly with `EADDRINUSE` and is corrected in seconds, whereas a block scheme imposes permanent friction: every project configured off its framework's default port, committed into each repo or remembered as a flag, to prevent a failure that is immediate and self-correcting. The port-forward case is being deliberately removed by ADR's M4 (issue #63), which replaces `kubectl port-forward` in the normal loop with Tailscale `Ingress` — optimising a workflow another milestone deletes is work against itself.
>
> What survives is weaker and differently justified: a **lookup table, not an allocation authority**, holding one stable dev port per project so `devx` (issue #62) knows which URL to open and M4's `Ingress` objects have a known `targetPort`. Rows are added when a project is actually onboarded rather than pre-allocated across 14 repos, and framework defaults (Vite 5173, Django 8000) are preferred — a project moves off its default only if it genuinely conflicts with something in its own pod. The table lives in `docs/Workbench Runbook.md`.
>
> **Amendment (2026-07-31, implementation) — M4 (#63) uses Cloudflare Tunnel + Traefik, not a Tailscale `Ingress` per frontend.** Every mention of "Tailscale `Ingress`" above and in ADR-0057 describes the original plan, written before a wider pattern already live elsewhere in the cluster was noticed: eight platform/admin UIs (`argocd`, `longhorn`, `grafana`, `prometheus`, the Traefik dashboard, `immich`, `whoami`, `argo-rollouts`) are already reached via `*.in.neovara.uk` → the same public `cloudflared` tunnel → Traefik's `websecure` entrypoint, gated by Cloudflare Access rather than tailnet membership. Reusing it for dev frontends (`kiroku-dev.in.neovara.uk`) means one exposure mechanism cluster-wide instead of two, at the cost of dev URLs being reachable from anywhere Access allows rather than tailnet-only. A per-frontend `IngressRoute`+`Middleware`, written in the project's own repo next to its dev `Deployment`/`Service`, replaces the per-frontend Tailscale node the original text assumed. One easy-to-lose requirement discovered live: the `IngressRoute` needs an explicit `tls: {}` — omitting it does not error, the router just silently registers as plain HTTP and never matches a `websecure` connection, 404ing every request while the pods stay perfectly healthy.

**Consequences:** Three real capabilities are given up, knowingly. (1) Service names must be prefixed by hand and the prefix is a convention, not an enforced constraint — a forgotten prefix collides with another project rather than being rejected. (2) There is no per-project `NetworkPolicy` boundary: every dev container in `workbench` can reach every other, so a project's dev Postgres is reachable from an unrelated project's dev server. Acceptable because all of it is one operator's own code on a private tailnet, and unacceptable the moment that stops being true. (3) There is no `kubectl delete ns kiroku` teardown button — removing a project means deleting its specific Deployments, Services, and workspace directory, a per-object operation instead of a single namespaced sweep. In exchange, one devbox, one PVC, one set of tools, and every repo on the same filesystem where cross-repo `grep` and `git` just work.

## ADR-0055 — RWO Longhorn volume for the workspace; Longhorn RWX rejected on small-file performance, not capability
**Status:** Accepted — `longhorn-workbench` StorageClass and PVC live and verified (2026-07-29): confirmed `dataLocality: best-effort` bound in-cluster, `WaitForFirstConsumer` correctly deferred binding until the devbox pod existed, and both `/workspace` and `/home/vscode` survived a full pod delete + reschedule (issue #59)

**Context:** ADR-0054's flat namespace is one way to dodge the namespaced-PVC constraint; a ReadWriteMany volume is the other, and it would have permitted per-project namespaces. Longhorn 1.12 does support RWX, so this is not a "the platform can't do it" rejection — the capability is present and would work. The question is what it costs every day. Longhorn implements RWX by running a **share-manager** pod that exports the underlying volume over **NFSv4**; every read and write from every consumer becomes an NFS round trip rather than a local filesystem operation. A development workspace is close to the pathological worst case for that: `node_modules` trees run to tens of thousands of tiny files, `.git` object stores are tens of thousands more, and build caches (`GOMODCACHE`, `.venv`, Vite's cache, compiler intermediates) are the same shape again. The operations that would pay the NFS tax are exactly the ones in the inner loop — `npm install`, `go build`, `git status`, and language-server indexing, which walks the entire tree on every cold start. Metadata-heavy small-file work is where NFS's per-operation latency compounds hardest, and this workspace is essentially nothing else.

**Decision:** The workspace is a **single ReadWriteOnce Longhorn PVC**, 50Gi or larger, mounted at `/workspace` and as `$HOME`, with one replica per ADR-0051. All consumers — the devbox and every project's app containers — therefore schedule onto the same node, which RWO enforces for free. `$HOME` is on the same volume specifically so VS Code's Remote-SSH server, once installed, survives a pod restart instead of being re-downloaded.

The workspace gets its **own StorageClass** rather than reusing an existing one, on the `dataLocality` grounds set out in the amendment below.

> **Amendment (2026-07-28, pre-implementation).** The original text chose between the existing classes on `allowVolumeExpansion`, asserting that the chart's `longhorn` class has it `false` and `longhorn-replicated` has it `true`. **Both are `true` on the live cluster**, so that criterion does not discriminate, and `longhorn-replicated` turns out not to be a tier at all — `k8s/longhorn/manifests/storageclass-replicated.yaml` documents it as a legacy name retained only because a bound PVC's `storageClassName` is immutable. The real differentiator is one this ADR originally missed: **`dataLocality`**.
>
> Longhorn runs the **engine** (which serves the block device) on the node where the pod is attached, and the **replica** (which owns the bytes) wherever it was scheduled; the two communicate over TCP. With `dataLocality: disabled` there is nothing requiring a single-replica volume's only copy to live on the node running the pod, so every read and write can cross the LAN. That is the same per-operation latency tax this ADR rejected RWX for — choosing RWO to dodge NFS round trips and then landing the replica on the other physical machine re-incurs the cost by another route. Confirmed live at the time of writing: 8 of 13 attached volumes on this cluster were running with their only replica on the other host, including `immich/immich-library` (350Gi) and `nextcloud/nextcloud-db`. Neither `longhorn` (explicitly `disabled`) nor `longhorn-replicated` (unset, inheriting the global `default-data-locality: disabled`) avoids this — and `dataLocality` appears nowhere in this repo, so it was never a decision, only an untouched upstream default.
>
> The workspace therefore uses a dedicated StorageClass, `longhorn-workbench` (`k8s/longhorn/manifests/storageclass-workbench.yaml`), with `dataLocality: "best-effort"`, `numberOfReplicas: "1"`, `allowVolumeExpansion: true`, `reclaimPolicy: Delete` (ADR-0063 — no backups by design, so `Retain` would only orphan volumes), and `volumeBindingMode: WaitForFirstConsumer`. That last one deliberately diverges from `storageclass-replicated.yaml`'s `Immediate` and its stated rationale that "there's nothing to gain by waiting for the scheduler" — true under `disabled`, false under `best-effort`, where provisioning before a pod exists places the replica on free space alone and then forces a full cross-LAN rebuild once the pod schedules elsewhere. `best-effort` is chosen over `strict-local` because it is **strictly dominant over `disabled` at no cost**: it constrains the Kubernetes scheduler not at all, and when a local replica cannot be placed (no space, disk offline) it degrades silently to exactly `disabled` behaviour rather than failing to attach. `strict-local` would be faster still — it bypasses the network stack entirely — but it hard-binds the volume to one node, which is the only one of the three that trades away scheduling freedom. Transient cost of `best-effort`: when the pod moves, Longhorn builds the local replica in the background while continuing to serve from the remote one, briefly holding two copies.
>
> Node preference is deliberately left unexpressed. Under `best-effort` the data follows the pod, so placement is a **Kubernetes scheduling concern** (`nodeSelector`/`nodeAffinity` on the devbox), not a Longhorn one; Longhorn's disk/node tags exist but reaching for them here would fight the CSI layer for something the scheduler already states plainly. Worth revisiting only if the space-based default lands the workspace on `k3s-worker-3`'s spinning HDD and that proves slower in practice than `k3s-worker-1`'s SSD.

**Consequences:** Local-disk-speed filesystem semantics in the inner loop — the thing being optimized for. Per-project namespaces are foreclosed as a consequence, which ADR-0054 already accepted on its own terms. Every `workbench` pod is pinned to whichever node the volume is currently attached on, so the namespace has no spread across the cluster — but per the amendment, that node is chosen by the *scheduler* placing the first pod, with the replica following under `best-effort`, not fixed in advance by the volume. A second, quieter argument reinforces the same conclusion: RWX's share-manager is **a single pod per volume**, so all consumers share one failure domain and one restart — the multi-writer story is less independent than "RWX" suggests, and losing that pod stalls every project at once rather than one. Revisit only if a genuine multi-node requirement appears, at which point the cost has to be re-measured against real repos, not assumed away.

## ADR-0056 — Credential-free git transport: `ext::kubectl exec` with `receive.denyCurrentBranch=updateInstead`
**Status:** Accepted (planned — issue #61)

**Context:** Code has to move between the MacBook and the devbox, and the obvious answers all require the cluster to hold a credential: give the devbox a GitHub PAT, or a deploy key, or an SSH key registered with the org, so it can `git clone`/`git pull`/`git push` for itself. Every one of those puts a long-lived credential with write access to real repositories inside a pod, which contradicts the same policy that ADR-0003 has enforced since Foundation and that ADR-0059 applies to the registry. The relevant observation is that git's wire protocol does not care about the transport — `git-receive-pack` reads a pack file from stdin and writes status to stdout, and *any* channel carrying those two streams is a valid git remote. `kubectl exec` is such a channel, and the Mac already holds a legitimate GitHub credential and legitimate cluster credentials.

**Decision:** The Mac pushes into the devbox over an exec pipe. On the pod side each repo sets `git config receive.denyCurrentBranch updateInstead`, so a push into the checked-out branch updates the working tree rather than being refused outright. On the Mac side the remote is `git remote add pod "ext::kubectl exec -i -n workbench deploy/devbox -- git-receive-pack /workspace/<repo>"`. Two details are load-bearing: the target is `deploy/devbox`, **not** a pod name, because pod names change on every reschedule; and the flag is `-i`, **never** `-it`, because a TTY performs line-ending translation that corrupts the binary pack stream. The round trip is proven both ways — push Mac→pod, edit on the pod, `git fetch pod` back to the Mac.

**Consequences:** The cluster holds no git credential of any kind and cannot pull, push, or enumerate an organization even if the devbox is fully compromised — the blast radius of that pod stops at the code already on its own volume. The cost is a discipline rule rather than a technical limitation: **one side is hot at a time, and you commit before switching.** Two clones of the same repo exist, so `--amend` plus force-push loops between them are out; ordinary commits during the day and a `git reset --soft origin/main` squash before publishing is the working pattern. The Mac clone stays closed in normal operation, or the language-server cost this whole milestone exists to remove quietly returns. `updateInstead` is deliberately kept as a **safety rail, not a nuisance**: it *rejects* a push into a dirty pod working tree, which is exactly right — the alternative would be silently overwriting uncommitted work on the other side. The offline flip is a documented two-command procedure: `git fetch pod` before disconnecting, `git push pod` on return.

## ADR-0057 — No build abstraction; commands run directly in the shell
**Status:** Accepted (planned — issue #60)

**Context:** An earlier shape of this design assumed a uniform target vocabulary — a `Makefile` per repo exposing `make test`, `make run`, `make lint` — so that a driver on the Mac could invoke a known command remotely without knowing anything about the project. That abstraction is real work: every repo needs one, every target has to be kept honest as the project's actual tooling changes, and the Makefile becomes a second, drifting description of how to build something that already knows how to build itself. It bought exactly one thing, and only under one assumption: a remote-exec transport that needed a fixed command name to invoke.

**Decision:** There is no build abstraction. Once the devbox is reachable as a real SSH host (ADR-0064) with an interactive shell and the source already in place, commands are typed directly: `go test -race ./...`, `npm run dev`, `python manage.py migrate`. No `Makefile` target vocabulary is introduced or maintained. The one place a command *is* written down declaratively is the `command` field of an app container's Deployment spec (ADR-0058), which runs that project's dev server unattended — that is a container specification, not a build abstraction, and it exists because nothing is there to type it.

**Consequences:** Zero abstraction to maintain, zero drift between what the Makefile claims and what the project actually needs, and no per-repo onboarding step before a project can be developed in-cluster. Each project keeps its own idiomatic commands, which is what its own documentation and its own contributors already assume. The cost is that there is no single command that works across every project — deliberate, since the abstraction that would have provided it only ever existed to serve a transport that SSH made unnecessary.

## ADR-0058 — Mounted-source hot reload instead of image rebuilds in the inner loop
**Status:** Accepted (planned — issue #64)

**Context:** The standard containerized inner loop is edit → build image → push → redeploy, and it is slow enough that a great deal of tooling (Tilt, Skaffold, DevSpace) exists purely to hide how slow it is. That tooling all works the same way: a daemon on the developer's machine watches local files and drives rebuilds. On a MacBook with no container runtime and a deliberate goal of running no file-watching daemons locally, that is precisely the thing being eliminated. Meanwhile the workspace PVC is already mounted by the devbox and already holds the source.

**Decision:** App containers mount the same workspace PVC as the devbox — `/workspace/kiroku` into each `kiroku` container — and run the project's own dev server with its own native hot reload, via a `command` in the Deployment spec so it starts unattended. Crucially, **dependency directories live on the PVC as well**: `node_modules`, `.venv`, and `GOMODCACHE` are all on the volume rather than baked into an image layer. Multi-container log tailing uses `stern` or `kubectl logs -f`, explicitly **not** Tilt — which would reintroduce exactly the local file-watching daemon this milestone removed.

**Consequences:** There is no image rebuild in the inner loop at all. An edit on the devbox appears in the browser through the dev server's own reload path, and — because dependency trees are on the volume too — even *adding a dependency* is `npm install` inside the running container, not a rebuild. Image rebuilds are needed only when the **base image** itself changes: a new language runtime or a new system package, realistically a handful of times per project per year, which is what reduces ADR-0059's build infrastructure from a daily-path dependency to occasional plumbing. The tradeoff is that the running dev container is no longer a faithful reproduction of a production image — its dependencies come from a mutable volume rather than a pinned layer — which is correct for a dev loop and precisely why ADR-0060 forbids this path from ever feeding Argo CD.

## ADR-0059 — In-cluster `registry:2` instead of ghcr.io, because containerd cannot read images from a PVC
**Status:** Accepted (planned — issue #65)

**Context:** ADR-0058 removes rebuilds from the daily loop but not from existence — a base-image change still needs a real build, and the Mac has no container runtime and will not get one, so builds run in-cluster from the devbox via `buildkitd`. That produces an image, which then has to reach the kubelet on whichever node runs the pod. The tempting shortcut — the built image is already on the workspace PVC, so point the Deployment at it — **does not work, and cannot be made to work**: `image:` is not a filesystem path, and containerd resolves images exclusively from its own per-node content store, populated only by pulling from a registry. A PVC is invisible to it. That single fact is why a registry is a **requirement** here rather than a convenience, and it is the second of the two Kubernetes constraints (with namespaced PVCs) that shaped this whole milestone. Given that a registry is mandatory, the choice is which one: ghcr.io, already associated with the operator's GitHub account, or something in-cluster.

**Status update (2026-07-29):** registry and `buildkitd` are live in `workbench` and verified — `curl http://registry.workbench.svc.cluster.local/v2/` returns `HTTP 200`, and BuildKit reports `found 1 workers` / `running server on [::]:1234`.

> **Amendment (2026-07-29, implementation) — namespace, ports, and the TLS question closed.** Three corrections to the original text.
>
> **Namespace.** The original `buildctl` example implied `registry.registry.svc` and `buildkitd.build.svc` — two new namespaces. Both components live in **`workbench`** instead: ADR-0054's flat-namespace argument applies unchanged, and the devbox's existing namespace-admin RoleBinding (ADR-0065) already covers them without further RBAC. The real names are `registry.workbench.svc.cluster.local` and `buildkit.workbench.svc`.
>
> **Ports.** Both Services listen on **port 80** (targeting 5000 and 1234), so image references carry no port suffix: `registry.workbench.svc.cluster.local/<repo>:dev`. Verified working — containerd parses the dotted name as a registry host rather than a Docker Hub path.
>
> **TLS, previously left open.** The original Consequences noted "issuing the registry a real certificate from the existing cert-manager remains open." **Closed: not worth it.** Both live ClusterIssuers are ACME/Let's Encrypt via DNS-01, which cannot issue for `registry.workbench.svc.cluster.local` — that is not a public DNS name. Option B would require creating a SelfSigned→CA issuer chain *and* distributing that CA to every node's trust store via Ansible (`/usr/local/share/ca-certificates/` is empty on all nodes today), *plus* `registries.yaml` anyway to point containerd at the right endpoint. That is strictly more moving parts than plain HTTP for the same "remember something when adding a node" cost, and it adds a CA-expiry failure mode that plain HTTP does not have. The registry is ClusterIP-only — reachable solely from inside the cluster on a private network — so plaintext here is a materially different risk class from an internet-facing registry.
>
> **The registry Service is `NodePort`, not `ClusterIP`, and the endpoint is a node-local address.** The original text's `registry.registry.svc:5000` endpoint cannot work, and the reason is structural rather than a config slip: **the thing that pulls images is containerd, running on the node.** Nodes sit outside the cluster network and use their own resolver, so they cannot resolve any `*.svc.cluster.local` name — that is CoreDNS's job, and CoreDNS only serves pods. Verified live: the pull failed with `dial tcp: lookup registry.workbench.svc.cluster.local: no such host`, and `getent hosts` on a node confirms it cannot resolve the name. This is [k3s issue #1581](https://github.com/k3s-io/k3s/issues/1581), open since March 2020 with no upstream fix; the workaround proposed there — adding CoreDNS's ClusterIP to each node's `/etc/resolv.conf` — is rejected because it makes every node's DNS depend on a pod that itself needs DNS to schedule.
>
> The resolution is the pattern kind, k3d, and minikube all converged on, and it turns on a detail that is easy to miss: **the `mirrors` key in `registries.yaml` is a matching pattern, not a hostname.** It is compared as a literal string against the image reference and is never resolved; only `endpoint` is ever dialed. So manifests and `buildctl` keep the readable `registry.workbench.svc.cluster.local/<repo>:dev` while containerd is pointed at `http://127.0.0.1:30500` — the Service's pinned `nodePort`. The name never has to work in both contexts, because it only ever has to work in one.
>
> `NodePort` was chosen over hardcoding the ClusterIP in `registries.yaml`: a ClusterIP is stable only until the Service is deleted and recreated, at which point every node's copy goes silently stale. `hostPort` was rejected outright as [known-broken with CNI plugins](https://github.com/kubernetes/kubernetes/issues/44564). This does not contradict the original "ClusterIP only" wording, which was written to mean *not exposed to the LAN*; a NodePort bound for node-local containerd use is narrower than what that guarded against, and pods still reach the registry by its ClusterIP unchanged. k3s's embedded registry mirror (Spegel) was also evaluated and does not apply — it is read-only and cannot accept pushes.
>
> **Acceptance verified end to end on 2026-07-29:** `buildctl` from the devbox built an image from a Dockerfile on the workspace PVC, pushed it to the in-cluster registry, and a pod on **each of the three nodes** pulled and ran it, printing the string baked in by the build's `RUN` instruction.
>
> **Rootless BuildKit needs `Unconfined` seccomp and AppArmor profiles**, not just `--oci-worker-no-process-sandbox`. Without them rootlesskit cannot create the user and mount namespaces it is built on and the container dies immediately with `failed to share mount point: /: permission denied`. `Unconfined` is not equivalent to `privileged`: the container still runs as a non-root user and cannot escape to the node; it only stops the kernel filtering the namespace syscalls. BuildKit gets an `emptyDir` rather than a PVC — the build cache is rebuildable by definition, so losing it costs one slow rebuild rather than any data.

**Decision:** A `registry:2` Deployment backed by a Longhorn PVC, ClusterIP only, inside the cluster. Builds run from the devbox — source is already on the volume, so nothing is shipped anywhere — via `buildctl --addr tcp://buildkitd.build.svc:1234 build --local context=/workspace/<repo> --output type=image,name=registry.registry.svc:5000/<repo>:dev,push=true`.

Public images are pulled without restriction. The original text wrote "no external credential anywhere in the cluster's image path," which was an overstatement. The actual constraint is narrower: the cluster holds **no work account credentials**, so an image that requires private-auth to pull cannot be used. But public images — Docker Hub, Microsoft's MCR, anywhere that serves without authentication — are permitted without limitation. The in-cluster registry exists specifically for **work-derived artifacts**, to keep those off a personal GitHub account and to avoid the credential question entirely for images you build yourself.

**Consequences:** No external credential anywhere in the cluster's image path. The cost is node-level trust configuration that a public registry would not need: `/etc/rancher/k3s/registries.yaml` must be present on **all three nodes** telling containerd to trust the in-cluster registry, managed through Ansible like every other node-level concern (the alternative — issuing the registry a real certificate from the existing cert-manager — remains open). That file is now part of what a new node needs before it can run `workbench` workloads, so adding a fourth node means remembering it. Acceptance is proven by the thing that motivated the decision: a pod on **any** node successfully pulling an image the devbox built.

## ADR-0060 — The in-cluster builder is dev-only and must never produce images Argo CD deploys
**Status:** Accepted (planned — issue #65)

**Context:** Once a working build path exists inside the cluster, the obvious next thought is to use it for real deployments too — build here, push here, let Argo CD deploy it, and skip CI entirely. That is exactly the failure mode GitOps exists to prevent. An image built ad hoc from a devbox's working tree is produced from whatever was on that PVC at that moment — possibly uncommitted, possibly with dependencies installed by hand into a mounted `node_modules` (ADR-0058) — with no commit SHA, no build record, and no way to reproduce it from git. Deploying such an artifact through Argo CD means the cluster's declared state points at something git cannot reconstruct, which quietly voids the entire "the repository is the source of truth" property that ADR-0042 through ADR-0048 were built to establish.

**Decision:** The in-cluster registry and builder are scoped to **development only**. Images they produce are consumed exclusively by `workbench` app containers and are never referenced by any Argo CD-managed Application. Real images for anything Argo CD deploys come from CI, tracked as issue #27. The dev tag namespace is kept visibly distinct (`:dev`) rather than sharing a tag vocabulary with production artifacts.

**Consequences:** A hard line rather than a guideline, stated here so that a future "just this once" has to argue against a written decision. The practical cost is that a real deployment still waits on CI (#27) — the in-cluster builder does not shortcut it, by design. The platform ends up with two image paths that must not be confused: a fast, unreproducible one for the inner loop, and a slow, reproducible, git-derived one for anything that reaches a GitOps-managed namespace.

## ADR-0061 — `workbench` under Argo CD with manual sync and `/spec/replicas` ignored
**Status:** Accepted — live and verified 2026-07-30 (issue #66)

**Context:** Every other namespace on this platform is managed by Argo CD with `automated` sync, and most with `selfHeal` — correct for infrastructure, where drift from the committed state is a defect. A development namespace inverts that assumption. It is poked at imperatively as a matter of routine: `devx <project> down` scales a project's containers to zero to reclaim node resources, containers get restarted, specs get edited live while something is being debugged. Under the platform's normal sync policy, scaling to zero would last only until the next reconcile, because git says `replicas: 1` and self-heal exists precisely to make live match git. Argo CD would spend the day undoing the workflow.

**Decision:** A **single** Argo CD `Application` for `k8s/workbench/manifests/` under the `default` AppProject — one Application, not an ApplicationSet, because ADR-0054 produced exactly one namespace and there is nothing to generate over (unrelated to issue #42).

> **Amendment (2026-07-28, pre-implementation).** The original text said `k8s/apps/personal/workbench/` under the `personal` AppProject. That is not possible as written and would not have been right if it were. `projects/personal.yaml` states that this repo must **never** appear in its `sourceRepos` — the project exists to fence *external, dev-owned* repos, on the principle that push access to a GitOps-watched repo is deploy access to the cluster. Workbench has no external repo; all its manifests live here. Following the original text would have required adding this repo to `sourceRepos`, adding `workbench` to `destinations`, and relaxing `clusterResourceWhitelist: []` to permit the `Namespace` — at which point `personal` would no longer fence anything.
>
> Inspection also showed the repo's directory layout **determines** the AppProject with no exceptions: all 8 top-level `k8s/<component>/` Applications run under `default`, all 3 `k8s/apps/homelab/<app>/` under `homelab`, and the sole `default` under `apps/` is `kiroku-governance`, whose own comments explain the exception. Placement therefore selects the project rather than being independent of it.
>
> `k8s/apps/homelab/workbench/` under the `homelab` project was the considered alternative and would have given real containment — that project already allow-lists this repo and whitelists exactly the `Namespace` kind — at the cost of one `destinations` line. It was rejected on fit: `projects/homelab.yaml` describes itself as the group for **off-the-shelf workloads** (homepage, nextcloud, audiobookshelf, immich), and workbench is not consumed like a service. It is development infrastructure, and by issue #65 it is literally a container registry and a build daemon, which belong beside Longhorn and Traefik rather than beside Audiobookshelf.
>
> The accepted cost is real and is recorded rather than glossed: `default` is `*`/`*`/`*` and applies **no containment at all**, so workbench gains no project-level fence. This is the same trust already extended to every other platform component, including cloudflared, which terminates an external tunnel. Revisit by promoting workbench to its own AppProject if the namespace ever runs code that is not the operator's own. `syncPolicy` is **manual**, with no `automated` block and no `selfHeal`. `ignoreDifferences` is set on `apps/Deployment` for `/spec/replicas`, so a scaled-to-zero project is not reported as drift and is not reverted. Secrets stay imperative and uncommitted, per the repo-wide constraint from ADR-0003. This adoption is deliberately the **last** milestone in the sequence: the shape gets to stop moving before it gets declared.

> **Amendment (2026-07-30, implementation) — the Application adopts infrastructure only; dev workloads are deliberately outside GitOps.** The original text assumed everything in `workbench` came from this repo. It does not. Per-project dev Deployments, Services, and Tailscale `Ingress` objects (`kiroku-api`, `kiroku-web`, …) are written in each **project's own repo** and applied with `kubectl` from the devbox, which holds namespace-admin here (ADR-0065). The `workbench` namespace is the operator's working environment, not a deployment target — putting its dev workloads under GitOps would add a commit-and-sync cycle to the inner loop that M5's whole design exists to remove.
>
> This changes two things about the Application. **`prune` must stay off** (it defaults false, and is left absent deliberately): prune asks "what is in the namespace that git does not specify?", which is a blunter question than the tracking-id comparison driving sync status, and with a namespace that intentionally holds foreign objects it is not a mechanism to leave armed. Removing a manifest from git therefore means deleting the object by hand — acceptable, since manual sync already means someone is present to review the diff.
>
> **No label scoping is needed**, contrary to the initial concern that unmanaged objects would leave the Application permanently `OutOfSync`. Argo compares git against objects carrying its own `argocd.argoproj.io/tracking-id` marker (this cluster uses the default `label` tracking method), not against the namespace contents; hand-applied objects carry no marker and never enter the comparison. Confirmed on the live cluster before relying on it — the `kiroku` Application reads `Synced` while an untracked `kube-root-ca.crt` ConfigMap sits in its namespace, and after adoption a hand-applied dev Deployment in `workbench` neither appeared in the Application's resource list nor changed its status.
>
> Adoption behaved as ADR-0044 predicted for a hand-applied bundle: all ten infrastructure objects reported `OutOfSync` before the first sync and `Synced`/`Healthy` after, on a tracking-annotation-only diff. Scaling the devbox to zero afterwards left the Application `Synced` and was not reverted, which is the `ignoreDifferences` and no-`selfHeal` combination doing its job.

**Consequences:** The workspace's structure is reproducible from git — a rebuild recreates the namespace, the PVC, the devbox, and every project's Deployments and Services — while the *runtime* state of replica counts remains the operator's to set imperatively. The tradeoff is that a genuine, unintended replica drift is now invisible to Argo CD, which is the price of the exemption and acceptable in a namespace whose whole purpose is to be changed by hand. Manual sync also means a commit to `workbench` manifests does not take effect until someone syncs, which is correct here — the same "review the diff before it lands" caution ADR-0044 applied to adoptions, kept permanently rather than as a first-sync precaution.

## ADR-0062 — `homelab-k8s` and `homelab` are excluded from in-cluster development
**Status:** Accepted (planned — issue #59)

**Context:** The devbox is intended to hold every repo the operator works on, and the two infrastructure repositories are the ones worked on most. They are also the two that cannot safely be developed from inside the cluster they describe. A `terraform apply` run from a pod scheduled on `k3s-worker-1` is executing inside a VM that the same Terraform state manages — it can destroy or replace its own execution environment partway through the apply, killing the process mid-operation and leaving the state file locked with real infrastructure in a partially-applied condition. Ansible runs against the k3s nodes have a milder version of the same problem, and a `kubectl apply` that reconfigures the cluster can sever the very exec channel ADR-0056 depends on.

**Decision:** `homelab-k8s` and `homelab` are explicitly out of scope for this workflow. They are not checked out onto the workspace volume and are not developed from the devbox. Both stay on the MacBook, or on a Proxmox VM outside the k3s cluster — a control point whose lifecycle is not owned by the thing it is changing.

**Consequences:** The "all my code is on the devbox" property has two named exceptions, and they are the exceptions most likely to be forgotten in a hurry, which is why they are written down as a decision rather than left to memory. The Mac therefore keeps a working Terraform/Ansible/kubectl toolchain — it does not become a *pure* thin client, only a thin client for application development. This also means an infrastructure change that breaks the cluster does not simultaneously destroy the environment needed to fix it, which is the property being bought.

## ADR-0063 — No backups for the workspace volume; GitHub is the backup and the rule is commit before you stop
**Status:** Accepted (planned — issue #67)

**Context:** The workspace PVC is a single-replica Longhorn volume (ADR-0051, ADR-0055) holding 14 repositories, every dependency tree, and every build cache. Losing the node that holds that replica makes the entire development environment unavailable until the node returns; losing the replica itself loses whatever was not pushed. The platform's full backup strategy — off-box etcd snapshot shipping, Velero, Proxmox Backup Server — is still deliberately deferred (see `ROADMAP.md`), so there is no existing mechanism to opt this volume into, and building one for this volume specifically would be a real piece of work.

**Decision:** **No backups of the workspace volume, by decision.** The durable copy of everything that matters is GitHub, reached via the ADR-0056 transport, and the operational rule that makes that true is *commit before you stop* — the same rule ADR-0056 already imposes for a different reason (one side hot at a time). No second Longhorn replica, no Velero schedule, no snapshot job. This is recorded explicitly so it reads as a considered choice rather than an oversight found later during an incident.

**Consequences:** A node loss makes the workspace **unavailable**, not destroyed — the volume returns with the node, and RWO scheduling (ADR-0055) means no pod runs against it in the meantime. What is genuinely at risk is uncommitted work, bounded by however long ago the last commit was, which is exactly the exposure the operating rule is designed to keep small. Everything else on the volume is reconstructible by definition: repositories re-clone from GitHub, and `node_modules`/`.venv`/`GOMODCACHE` re-install from their lockfiles. Revisit if the workspace ever accumulates something that is neither committed nor reproducible — at which point the right fix is to stop keeping such a thing there, not to add a backup for it.

## ADR-0064 — Tailscale SSH in the devbox container, not an operator-exposed Service on port 22
**Status:** Accepted — live and verified 2026-07-29; the "sidecar" mechanism is **superseded by the amendment below** (issue #60)

**Context:** The devbox has to be reachable as an SSH host from the MacBook, because VS Code Remote-SSH is the mechanism that moves the language server off the laptop — the largest single battery win in this milestone. This platform already has two established ways to expose something over the tailnet (ADR-0018): the Tailscale Operator's `loadBalancerClass: tailscale` Service, and its `Ingress`. Either could put port 22 on the tailnet, but both presuppose there *is* a port 22 — meaning a real `sshd` inside the devbox, with host keys to generate and persist, an `authorized_keys` file to manage, and a second authentication system to keep correct alongside the tailnet's own. Tailscale SSH removes that entire layer: `tailscaled --ssh` terminates SSH itself, authenticating the connection against tailnet identity and authorizing it against the tailnet ACL, with no SSH daemon, no host key, and no key file in the pod at all.

**Decision:** The devbox pod runs **`tailscaled --ssh` inside the devbox container itself** (see the amendment below — the original text said "sidecar container," which cannot work), joining the tailnet as its own node, rather than exposing port 22 through an operator-managed Service.

> **Amendment (2026-07-29, implementation) — the sidecar mechanism is wrong; `tailscaled` runs in the devbox container.** The original decision specified a Tailscale **sidecar container**. That cannot work, for a reason the ADR never checked: **Tailscale SSH is terminated by `tailscaled` itself, which spawns the login shell as its own child, in its own container's filesystem.** Containers in a pod share a network namespace but not a filesystem or PID namespace, so `ssh workbench` against a sidecar lands in the *sidecar*, not the devbox — with no `/workspace`, no `mise`, no `tmux`, no `vscode` user. Worse, the official `tailscale/tailscale` image is **Alpine/musl**, so the shell would land in exactly the environment this same ADR rejects two sentences later for breaking VS Code Remote-SSH's glibc-linked server. Sharing the process namespace and mounting the PVC into the sidecar does not fix it, because the incompatible *filesystem* is the problem.
>
> `tailscaled` therefore runs **in the devbox container**, started from the container's `command`/`args` and supervised by a `livenessProbe` running `tailscale status` rather than by a separate container. Three implementation details are load-bearing and were each found the hard way:
>
> 1. **`--statedir=<dir>`, not `--state=<file>`.** Tailscale SSH generates host keys and needs a state *directory* ("var root") to write them into. With only `--state`, `tailscaled` starts, exits 0, and advertises the SSH capability, but logs `SSH will appear as disabled for this node` and never serves port 22. The symptom is a TCP connection that hangs at banner exchange — indistinguishable from a network fault.
> 2. **The state directory lives on the PVC** (`$HOME/.local/share/tailscale`), which is what makes the node *identity* durable. Verified: after a full pod delete, `tailscaled` resumed as the same node with **no auth key and no `tailscale up`**. Without this, every restart registers a new node and the MagicDNS name drifts (`workbench-1`, `-2`, …) because Tailscale will not reuse a name still held by a non-ephemeral registration.
> 3. **`setsid … </dev/null` and `exec sleep infinity`.** Backgrounding `tailscaled` from a `kubectl exec` session kills it when that session ends; `setsid` detaches it. And `exec` on the foreground process makes `sleep` PID 1, so `SIGTERM` reaches it directly — without `exec`, bash is PID 1, does not forward the signal, and every pod deletion waits out the full termination grace period.
>
> Userspace networking (`--tun=userspace-networking`) was verified sufficient: **no `NET_ADMIN`, no `/dev/net/tun`, no root**, so the pod keeps `runAsNonRoot: true` / `runAsUser: 1000` from ADR-0055's uid alignment. The pod-level alternative — a native sidecar (`initContainers` with `restartPolicy: Always`, stable since 1.33 and available on this 1.36 cluster) — is the textbook-correct shape for a helper process and is nonetheless *wrong here* for the filesystem reason above. The cost of running `tailscaled` in-container is that it is not PID 1 and so is invisible to the kubelet's normal restart logic; the `livenessProbe` restores that supervision by health-checking the daemon directly.
>
> One consequence remains open: `tailscaled` is installed at runtime into the PVC-backed `$HOME` rather than baked into the image, so a recreated volume leaves the Deployment starting a binary that does not exist. Deliberate — image builds need BuildKit (issue #65) — but a known state, not a surprise.

Access is granted by a `tag:devbox` ACL rule so it is one grant rather than a per-host entry, and the same tagging pattern extends to the per-frontend Tailscale `Ingress` nodes so the ACL stays a single rule regardless of how many dev frontends exist. The devbox image is **Debian-slim based, not Alpine** — VS Code Remote-SSH's server is dynamically linked against glibc and does not run on musl, so Alpine breaks the primary use case outright. Acceptance is `ssh workbench` working from the Mac, VS Code Remote-SSH attaching and installing its server into `$HOME`, that server surviving a pod restart (which is why `$HOME` is on the PVC, ADR-0055), and no language-server process running on the Mac during a normal session — **all verified live on 2026-07-29.**

**Consequences:** No sshd, no host keys, no `authorized_keys`, and no credential material in the devbox image — authentication and authorization are both the tailnet's, managed in one place with everything else on it. The devbox appears as an ordinary tailnet node, so `ssh workbench` works from any authorized device without per-device setup. The base-image constraint is a real one and worth remembering: the natural instinct for a small dev image is Alpine, and choosing it here would silently break Remote-SSH in a way that looks like a networking problem. The accepted cost across this milestone is one tailnet node per exposed thing — the devbox plus one per exposed dev frontend — which the tag-based ACL keeps from turning into per-host policy sprawl.

## ADR-0065 — The devbox holds namespace-admin on `workbench`, secrets included
**Status:** Accepted — live and verified 2026-07-29 (issue #60)

**Context:** The devbox needs enough Kubernetes access to be useful from inside itself — restart its own Deployments, read its own logs, and manage the Secrets that dev workloads in `workbench` consume. It is also, by design, the one pod on this platform that routinely executes arbitrary third-party code: every `npm install` is remote code execution, and that is the point of the machine, not a flaw in it. Two facts framed the decision. First, a pod with no `serviceAccountName` silently gets the namespace's `default` ServiceAccount **and a mounted API token**, so "do nothing" is not the same as "no credential" — verified here, and separately verified that the `default` SA on this cluster is bound to nothing and can do essentially nothing. Second, this repo already set a contrary precedent: `k8s/apps/personal/kiroku/rbac.yaml` hand-writes a `Role` specifically to *exclude* `secrets`, on the grounds that a deployer identity handed to a collaborator or CI has no business reading them.

**Decision:** A dedicated `devbox` ServiceAccount bound to the **built-in `admin` ClusterRole via a namespaced `RoleBinding`** — full namespace-admin on `workbench`, `secrets` included, and nothing outside it. The mechanism is the load-bearing part: a `RoleBinding` that references a `ClusterRole` grants that ClusterRole's permissions **only within the binding's namespace**. The `ClusterRole` is the permission *definition*; the *binding kind* determines scope. Binding this same `admin` role with a `ClusterRoleBinding` would be cluster-wide, which is the mistake this shape exists to avoid. This is a deliberate divergence from the `kiroku` deployer precedent, on threat model rather than convenience: that identity is handed to a third party, whereas this is the operator's own development environment, poked at imperatively by design (ADR-0061), where enumerating every verb a day's work might need is friction that buys little.

**Consequences:** `kubectl` works from inside the devbox for its own namespace and fails outside it. Verified with the ServiceAccount's real token from inside the pod — `200` on `workbench` secrets and deployments, `403` on `longhorn-system` secrets, cluster-wide secrets, and nodes. That verification method matters: `kubectl auth can-i --list --as=<sa>` reported blanket `*.*` for this SA, because the operator holds cluster-admin through ADR-0026's Tailscale RBAC and the impersonation form leaked the caller's own effective permissions into the answer. **When the answer matters, test with the credential, not with `--as`.** The accepted risk, recorded once rather than left implicit: `admin` includes read/write on `secrets`, the `tailscale-auth` key lives in this namespace, and arbitrary code running in the devbox can therefore read it and join the tailnet. Accepted knowingly — an equivalent local development machine already holds broader credentials than this — with the mitigation noted for later if it stops being true: move tailnet credentials to their own namespace, or replace this binding with a hand-written `Role` that omits `secrets`.

## ADR-0066 — `devx` discovers workloads by label, and encodes lifecycle in the manifest
**Status:** Accepted — live and verified 2026-07-30 (issue #62)

**Context:** M3 asks for one command that takes you from a cold cluster to a working shell. The obvious implementation keeps a config file mapping project names to the Deployments they own, and hardcodes which of those survive a `down`. Both halves are a second source of truth: the config drifts from the manifests the moment a workload is renamed, and "leave Postgres running" living inside a shell script means the fact is invisible to anyone reading the Deployment. The tool also has to decide what it is *not* — the original sketch had it managing `kubectl port-forward` tunnels, which is the messiest thing a tool like this can own.

**Decision:** Workloads are discovered entirely by label. Every project Deployment carries `workbench.neovara/project: <name>`, so `kubectl scale deploy -l workbench.neovara/project=kiroku` works with or without `devx`; a second label, `workbench.neovara/lifecycle: always-on | on-demand`, encodes which workloads `devx <project> down` scales to zero. Long-lived Postgres is `always-on` because cold-starting a database mid-thought is the most disruptive possible interruption, and that fact now lives in the manifest rather than in a script. "Up" always means `--replicas=1`: scaling to zero destroys the prior value, but every dev workload here is single-replica by definition, so recording and restoring it would be machinery for a case that does not exist.

`devx` owns no tunnels — M4's Tailscale `Ingress` per frontend removes that need entirely. It owns no build vocabulary either, per ADR-0057: it gets you to a shell and stops. The connect line is `ssh -A -t workbench "tmux new -A -s <project> -c /workspace/<project>"`, where the two `-A` flags are unrelated and both load-bearing — ssh's forwards the agent so git needs no credential on the PVC, and tmux's is attach-or-create, which makes reconnecting after a dropped tailnet link the *same command* as connecting fresh. **Cluster-unreachable is treated as a supported mode, not an error**: every path that needs the API checks reachability first and prints what to do, because a raw `kubectl` timeout arrives at exactly the moment it is hardest to debug.

Written in bash and shipped in the repo at `bin/devx`, symlinked onto `PATH`, rather than as a stray script in `~/bin`. Go was tempting and would be better practice, but the tool's shape is not yet known and the second version is always better; bash makes the first one cheap. Revisit as a Go rewrite once it has survived a month of daily use and has a real spec.

**Consequences:** Adding a workload to a project is a label on its Deployment and nothing else — no `devx` change, no config edit, and the same labels work from plain `kubectl` when `devx` is not involved. The convention is unenforced, so a Deployment missing the project label is simply invisible to the tool; `devx ls` exists partly to make that obvious. Two constraints from the original M3 sketch turned out to be stale and were dropped rather than implemented: the per-project **port block**, which the ADR-0054 amendment eliminated once it was clear pods have their own network namespaces, and `devx pull` as a `git fetch pod` against ADR-0056's exec transport, which issue #61 skipped — `pull` now reports the pod's uncommitted state and prints the remote recipe instead of pretending a transport exists.

One portability constraint is worth recording because it is invisible until it bites: **macOS ships bash 3.2**, which predates `mapfile`/`readarray`. Requiring a Homebrew bash 5 would make the tool's first instruction "install a different shell", so `devx` uses a portable `read_lines_into` helper and is tested against `/bin/bash` explicitly. This was found the hard way — the first real `devx down` failed with `mapfile: command not found`.
