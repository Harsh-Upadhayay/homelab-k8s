# v4.0 — Developer Workspace (ADR-0054 … ADR-0064)

> Back to [[Homelab Learning Map]] · Previous [[v2.0 - Operability]] · Index [[README|ADR index]]

Every milestone up to here treated the cluster as somewhere to *run* things and the MacBook as where they get *written*. This one moves the writing across the wire too. Development leaves the laptop entirely: the devbox pod holds the checkout, the language server, the dependency caches, the compilers and the test runs, and the Mac becomes a thin client — no container runtime, no language server, no local builds, nothing but a terminal and VS Code's Remote-SSH front half. The win is concrete and measurable in battery: the single largest sustained consumer during a normal working day is a language server indexing a repo, and that process now runs on hardware that is plugged into a wall.

Two Kubernetes facts, neither of them negotiable, did most of the architectural work here. **PVCs are namespaced** — a volume cannot be mounted from a namespace it does not live in — which is what collapses the natural "one namespace per project" instinct into a single flat `workbench` namespace (ADR-0054), because the alternative is either a devbox per project or a shared RWX volume, and RWX is separately rejected on performance grounds (ADR-0055). **containerd reads images only from its own per-node content store** — an image sitting on a PVC is invisible to the kubelet no matter how the manifest is written — which is why an in-cluster registry is a hard requirement rather than a nicety (ADR-0059). Everything else in this log follows from those two constraints plus one policy line: no external credential ever enters this cluster.

That policy line is what makes the git story interesting. The Mac already legitimately holds a GitHub credential; the cluster does not and will not. Git will run its wire protocol over any transport that carries stdin and stdout, and `kubectl exec` is one, so code moves by pushing a pack file down an exec pipe rather than by giving the cluster a PAT or a deploy key (ADR-0056). A compromised devbox cannot pull, push, or even enumerate an org, because there is nothing there to do it with.

The remaining decisions are mostly about *not* building things. No Makefile target vocabulary, because the abstraction only ever existed to feed a remote-exec transport that SSH made unnecessary (ADR-0057). No image rebuild in the inner loop, because source and dependency directories both live on the PVC (ADR-0058). No CI role for the in-cluster builder, ever, because artifacts that Argo CD deploys must be reproducible from git (ADR-0060). No auto-sync or self-heal on the `workbench` Application, because a dev namespace is poked at imperatively by design and Argo would spend its day undoing that (ADR-0061). No in-cluster development of `homelab-k8s` or `homelab` at all, because a `terraform apply` running on the cluster it provisions can delete its own execution environment mid-apply (ADR-0062). And no backups of the workspace volume — stated as a decision rather than left as a gap, because GitHub is the real backup and the operational rule is *commit before you stop* (ADR-0063). The one thing genuinely added rather than declined is the access path: a Tailscale sidecar running real Tailscale SSH, with no sshd, no host keys, and no `authorized_keys` file anywhere (ADR-0064).

## ADR-0054 — One flat `workbench` namespace holding the devbox and every project's app containers
**Status:** Accepted (planned — issue #59)

**Context:** The instinct was one namespace per project — `kiroku`, `ai-scraping`, and so on — matching how the platform already separates operators (ADR-0045's one-namespace-per-operator pattern) and how every Kubernetes tutorial models multi-tenancy. That instinct dies on a single fact: **PersistentVolumeClaims are namespaced objects**, and a pod can only mount a PVC that lives in its own namespace. The whole premise of this milestone is one workspace volume holding all 14 repos plus their dependency directories, mounted simultaneously by the devbox (where code is edited) and by each project's app containers (where it runs, per ADR-0058). Per-project namespaces therefore force one of exactly two things: a separate devbox pod per namespace, each with its own PVC — which multiplies the workspace, the tool installs, the VS Code server, and the storage footprint by the project count and destroys the "one shell, all my code" property that motivated the design — or a single ReadWriteMany volume shared across namespaces, which ADR-0055 rejects independently on performance.

**Decision:** A single `workbench` namespace, labeled `group: personal` and living under the existing `personal` AppProject, holds the devbox pod and every project's app containers together. One PVC, one devbox, one flat pool of Deployments and Services. Project separation is expressed by naming convention rather than by namespace boundary: service names are project-prefixed (`kiroku-api`, `kiroku-postgres`, never bare `api`/`postgres`), and dev-server ports are allocated in per-project blocks recorded in a table (kiroku 5173–5179, ai_scraping 5180–5189, …) so several dev servers coexist without collision. Dev hostnames are also disambiguated against live workloads — `kiroku` already runs in-cluster, so its dev exposure is `kiroku-dev`.

**Consequences:** Three real capabilities are given up, knowingly. (1) Service names must be prefixed by hand and the prefix is a convention, not an enforced constraint — a forgotten prefix collides with another project rather than being rejected. (2) There is no per-project `NetworkPolicy` boundary: every dev container in `workbench` can reach every other, so a project's dev Postgres is reachable from an unrelated project's dev server. Acceptable because all of it is one operator's own code on a private tailnet, and unacceptable the moment that stops being true. (3) There is no `kubectl delete ns kiroku` teardown button — removing a project means deleting its specific Deployments, Services, and workspace directory, a per-object operation instead of a single namespaced sweep. In exchange, one devbox, one PVC, one set of tools, and every repo on the same filesystem where cross-repo `grep` and `git` just work.

## ADR-0055 — RWO Longhorn volume for the workspace; Longhorn RWX rejected on small-file performance, not capability
**Status:** Accepted (planned — issue #59)

**Context:** ADR-0054's flat namespace is one way to dodge the namespaced-PVC constraint; a ReadWriteMany volume is the other, and it would have permitted per-project namespaces. Longhorn 1.12 does support RWX, so this is not a "the platform can't do it" rejection — the capability is present and would work. The question is what it costs every day. Longhorn implements RWX by running a **share-manager** pod that exports the underlying volume over **NFSv4**; every read and write from every consumer becomes an NFS round trip rather than a local filesystem operation. A development workspace is close to the pathological worst case for that: `node_modules` trees run to tens of thousands of tiny files, `.git` object stores are tens of thousands more, and build caches (`GOMODCACHE`, `.venv`, Vite's cache, compiler intermediates) are the same shape again. The operations that would pay the NFS tax are exactly the ones in the inner loop — `npm install`, `go build`, `git status`, and language-server indexing, which walks the entire tree on every cold start. Metadata-heavy small-file work is where NFS's per-operation latency compounds hardest, and this workspace is essentially nothing else.

**Decision:** The workspace is a **single ReadWriteOnce Longhorn PVC**, 50Gi or larger, mounted at `/workspace` and as `$HOME`, with one replica per ADR-0051. All consumers — the devbox and every project's app containers — therefore schedule onto the same node, which RWO enforces for free. `$HOME` is on the same volume specifically so VS Code's Remote-SSH server, once installed, survives a pod restart instead of being re-downloaded.

The workspace gets its **own StorageClass** rather than reusing an existing one, on the `dataLocality` grounds set out in the amendment below.

> **Amendment (2026-07-28, pre-implementation).** The original text chose between the existing classes on `allowVolumeExpansion`, asserting that the chart's `longhorn` class has it `false` and `longhorn-replicated` has it `true`. **Both are `true` on the live cluster**, so that criterion does not discriminate, and `longhorn-replicated` turns out not to be a tier at all — `k8s/longhorn/manifests/storageclass-replicated.yaml` documents it as a legacy name retained only because a bound PVC's `storageClassName` is immutable. The real differentiator is one this ADR originally missed: **`dataLocality`**.
>
> Longhorn runs the **engine** (which serves the block device) on the node where the pod is attached, and the **replica** (which owns the bytes) wherever it was scheduled; the two communicate over TCP. With `dataLocality: disabled` there is nothing requiring a single-replica volume's only copy to live on the node running the pod, so every read and write can cross the LAN. That is the same per-operation latency tax this ADR rejected RWX for — choosing RWO to dodge NFS round trips and then landing the replica on the other physical machine re-incurs the cost by another route. Confirmed live at the time of writing: 8 of 13 attached volumes on this cluster were running with their only replica on the other host, including `immich/immich-library` (350Gi) and `nextcloud/nextcloud-db`. Neither `longhorn` (explicitly `disabled`) nor `longhorn-replicated` (unset, inheriting the global `default-data-locality: disabled`) avoids this — and `dataLocality` appears nowhere in this repo, so it was never a decision, only an untouched upstream default.
>
> The workspace therefore uses a dedicated StorageClass, `longhorn-workbench` (`k8s/longhorn/manifests/storageclass-workbench.yaml`), with `dataLocality: "best-effort"`, `numberOfReplicas: "1"`, `allowVolumeExpansion: true`, `reclaimPolicy: Delete` (ADR-0063 — no backups by design, so `Retain` would only orphan volumes), and `volumeBindingMode: WaitForFirstConsumer`. That last one deliberately diverges from `storageclass-replicated.yaml`'s `Immediate` and its stated rationale that "there's nothing to gain by waiting for the scheduler" — true under `disabled`, false under `best-effort`, where provisioning before a pod exists places the replica on free space alone and then forces a full cross-LAN rebuild once the pod schedules elsewhere. `best-effort` is chosen over `strict-local` because it is **strictly dominant over `disabled` at no cost**: it constrains the Kubernetes scheduler not at all, and when a local replica cannot be placed (no space, disk offline) it degrades silently to exactly `disabled` behaviour rather than failing to attach. `strict-local` would be faster still — it bypasses the network stack entirely — but it hard-binds the volume to one node, which is the only one of the three that trades away scheduling freedom. Transient cost of `best-effort`: when the pod moves, Longhorn builds the local replica in the background while continuing to serve from the remote one, briefly holding two copies.
>
> Node preference is deliberately left unexpressed. Under `best-effort` the data follows the pod, so placement is a **Kubernetes scheduling concern** (`nodeSelector`/`nodeAffinity` on the devbox), not a Longhorn one; Longhorn's disk/node tags exist but reaching for them here would fight the CSI layer for something the scheduler already states plainly. Worth revisiting only if the space-based default lands the workspace on `k3s-worker-3`'s spinning HDD and that proves slower in practice than `k3s-worker-1`'s SSD.

**Consequences:** Local-disk-speed filesystem semantics in the inner loop — the thing being optimized for. Per-project namespaces are foreclosed as a consequence, which ADR-0054 already accepted on its own terms. Every `workbench` pod is pinned to whichever node the volume is currently attached on, so the namespace has no spread across the cluster — but per the amendment, that node is chosen by the *scheduler* placing the first pod, with the replica following under `best-effort`, not fixed in advance by the volume. A second, quieter argument reinforces the same conclusion: RWX's share-manager is **a single pod per volume**, so all consumers share one failure domain and one restart — the multi-writer story is less independent than "RWX" suggests, and losing that pod stalls every project at once rather than one. Revisit only if a genuine multi-node requirement appears, at which point the cost has to be re-measured against real repos, not assumed away.

## ADR-0056 — Credential-free git transport: `ext::kubectl exec` with `receive.denyCurrentBranch=updateInstead`
**Status:** Accepted (planned — issue #61)

**Context:** Code has to move between the MacBook and the devbox, and the obvious answers all require the cluster to hold a credential: give the devbox a GitHub PAT, or a deploy key, or an SSH key registered with the org, so it can `git clone`/`git pull`/`git push` for itself. Every one of those puts a long-lived credential with write access to real repositories inside a pod, which contradicts the same policy that ADR-0003 has enforced since Foundation and that ADR-0059 applies to the registry. The relevant observation is that git's wire protocol does not care about the transport — `git-receive-pack` reads a pack file from stdin and writes status to stdout, and *any* channel carrying those two streams is a valid git remote. `kubectl exec` is such a channel, and the Mac already holds a legitimate GitHub credential and legitimate cluster credentials.

**Decision:** The Mac pushes into the devbox over an exec pipe. On the pod side each repo sets `git config receive.denyCurrentBranch updateInstead`, so a push into the checked-out branch updates the working tree rather than being refused outright. On the Mac side the remote is `git remote add pod "ext::kubectl exec -i -n workbench deploy/devbox -- git-receive-pack /workspace/<repo>"`. Two details are load-bearing: the target is `deploy/devbox`, **not** a pod name, because pod names change on every reschedule; and the flag is `-i`, **never** `-it`, because a TTY performs line-ending translation that corrupts the binary pack stream. The round trip is proven both ways — push Mac→pod, edit on the pod, `git fetch pod` back to the Mac.

**Consequences:** The cluster holds no git credential of any kind and cannot pull, push, or enumerate an organization even if the devbox is fully compromised — the blast radius of that pod stops at the code already on its own volume. The cost is a discipline rule rather than a technical limitation: **one side is hot at a time, and you commit before switching.** Two clones of the same repo exist, so `--amend` plus force-push loops between them are out; ordinary commits during the day and a `git reset --soft origin/main` squash before publishing is the working pattern. The Mac clone stays closed in normal operation, or the language-server cost this whole milestone exists to remove quietly returns. `updateInstead` is deliberately kept as a **safety rail, not a nuisance**: it *rejects* a push into a dirty pod working tree, which is exactly right — the alternative would be silently overwriting uncommitted work on the other side. The offline flip is a documented two-command procedure: `git fetch pod` before disconnecting, `git push pod` on return.

## ADR-0057 — No build abstraction; commands run directly in the shell
**Status:** Accepted (planned — issue #60)

**Context:** An earlier shape of this design assumed a uniform target vocabulary — a `Makefile` per repo exposing `make test`, `make run`, `make lint` — so that a driver on the Mac could invoke a known command remotely without knowing anything about the project. That abstraction is real work: every repo needs one, every target has to be kept honest as the project's actual tooling changes, and the Makefile becomes a second, drifting description of how to build something that already knows how to build itself. It bought exactly one thing, and only under one assumption: a remote-exec transport that needed a fixed command name to invoke.

**Decision:** There is no build abstraction. Once the devbox is reachable as a real SSH host (ADR-0064) with an interactive shell and the source already in place, commands are typed directly: `go test -race ./...`, `npm run dev`, `python manage.py migrate`. No `Makefile` target vocabulary is introduced or maintained. The one place a command *is* written down declaratively is the `command` field of an app container's Deployment spec (ADR-0058), which runs that project's dev server unattended — that is a container specification, not a build abstraction, and it exists because nothing is there to type it.

**Consequences:** Zero abstraction to maintain, zero drift between what the Makefile claims and what the project actually needs, and no per-repo onboarding step before a project can be developed in-cluster. Each project keeps its own idiomatic commands, which is what its own documentation and its own contributors already assume. The cost is that there is no single command that works across every project — deliberate, since the abstraction that would have provided it only ever existed to serve a transport that SSH made unnecessary.

## ADR-0058 — Mounted-source hot reload instead of image rebuilds in the inner loop
**Status:** Accepted (planned — issue #64)

**Context:** The standard containerized inner loop is edit → build image → push → redeploy, and it is slow enough that a great deal of tooling (Tilt, Skaffold, DevSpace) exists purely to hide how slow it is. That tooling all works the same way: a daemon on the developer's machine watches local files and drives rebuilds. On a MacBook with no container runtime and a deliberate goal of running no file-watching daemons locally, that is precisely the thing being eliminated. Meanwhile the workspace PVC is already mounted by the devbox and already holds the source.

**Decision:** App containers mount the same workspace PVC as the devbox — `/workspace/kiroku` into each `kiroku` container — and run the project's own dev server with its own native hot reload, via a `command` in the Deployment spec so it starts unattended. Crucially, **dependency directories live on the PVC as well**: `node_modules`, `.venv`, and `GOMODCACHE` are all on the volume rather than baked into an image layer. Multi-container log tailing uses `stern` or `kubectl logs -f`, explicitly **not** Tilt — which would reintroduce exactly the local file-watching daemon this milestone removed.

**Consequences:** There is no image rebuild in the inner loop at all. An edit on the devbox appears in the browser through the dev server's own reload path, and — because dependency trees are on the volume too — even *adding a dependency* is `npm install` inside the running container, not a rebuild. Image rebuilds are needed only when the **base image** itself changes: a new language runtime or a new system package, realistically a handful of times per project per year, which is what reduces ADR-0059's build infrastructure from a daily-path dependency to occasional plumbing. The tradeoff is that the running dev container is no longer a faithful reproduction of a production image — its dependencies come from a mutable volume rather than a pinned layer — which is correct for a dev loop and precisely why ADR-0060 forbids this path from ever feeding Argo CD.

## ADR-0059 — In-cluster `registry:2` instead of ghcr.io, because containerd cannot read images from a PVC
**Status:** Accepted (planned — issue #65)

**Context:** ADR-0058 removes rebuilds from the daily loop but not from existence — a base-image change still needs a real build, and the Mac has no container runtime and will not get one, so builds run in-cluster from the devbox via `buildkitd`. That produces an image, which then has to reach the kubelet on whichever node runs the pod. The tempting shortcut — the built image is already on the workspace PVC, so point the Deployment at it — **does not work, and cannot be made to work**: `image:` is not a filesystem path, and containerd resolves images exclusively from its own per-node content store, populated only by pulling from a registry. A PVC is invisible to it. That single fact is why a registry is a **requirement** here rather than a convenience, and it is the second of the two Kubernetes constraints (with namespaced PVCs) that shaped this whole milestone. Given that a registry is mandatory, the choice is which one: ghcr.io, already associated with the operator's GitHub account, or something in-cluster.

**Decision:** A `registry:2` Deployment backed by a Longhorn PVC, ClusterIP only, inside the cluster. Builds run from the devbox — source is already on the volume, so nothing is shipped anywhere — via `buildctl --addr tcp://buildkitd.build.svc:1234 build --local context=/workspace/<repo> --output type=image,name=registry.registry.svc:5000/<repo>:dev,push=true`. ghcr.io is rejected on two independent grounds: it would require a registry credential to exist inside the cluster, contradicting the same no-external-credentials line that ADR-0056 holds for git; and it would place work-derived container artifacts on a personal GitHub account, which is a boundary worth keeping clean regardless of the technical question.

**Consequences:** No external credential anywhere in the cluster's image path. The cost is node-level trust configuration that a public registry would not need: `/etc/rancher/k3s/registries.yaml` must be present on **all three nodes** telling containerd to trust the in-cluster registry, managed through Ansible like every other node-level concern (the alternative — issuing the registry a real certificate from the existing cert-manager — remains open). That file is now part of what a new node needs before it can run `workbench` workloads, so adding a fourth node means remembering it. Acceptance is proven by the thing that motivated the decision: a pod on **any** node successfully pulling an image the devbox built.

## ADR-0060 — The in-cluster builder is dev-only and must never produce images Argo CD deploys
**Status:** Accepted (planned — issue #65)

**Context:** Once a working build path exists inside the cluster, the obvious next thought is to use it for real deployments too — build here, push here, let Argo CD deploy it, and skip CI entirely. That is exactly the failure mode GitOps exists to prevent. An image built ad hoc from a devbox's working tree is produced from whatever was on that PVC at that moment — possibly uncommitted, possibly with dependencies installed by hand into a mounted `node_modules` (ADR-0058) — with no commit SHA, no build record, and no way to reproduce it from git. Deploying such an artifact through Argo CD means the cluster's declared state points at something git cannot reconstruct, which quietly voids the entire "the repository is the source of truth" property that ADR-0042 through ADR-0048 were built to establish.

**Decision:** The in-cluster registry and builder are scoped to **development only**. Images they produce are consumed exclusively by `workbench` app containers and are never referenced by any Argo CD-managed Application. Real images for anything Argo CD deploys come from CI, tracked as issue #27. The dev tag namespace is kept visibly distinct (`:dev`) rather than sharing a tag vocabulary with production artifacts.

**Consequences:** A hard line rather than a guideline, stated here so that a future "just this once" has to argue against a written decision. The practical cost is that a real deployment still waits on CI (#27) — the in-cluster builder does not shortcut it, by design. The platform ends up with two image paths that must not be confused: a fast, unreproducible one for the inner loop, and a slow, reproducible, git-derived one for anything that reaches a GitOps-managed namespace.

## ADR-0061 — `workbench` under Argo CD with manual sync and `/spec/replicas` ignored
**Status:** Accepted (planned — issue #66)

**Context:** Every other namespace on this platform is managed by Argo CD with `automated` sync, and most with `selfHeal` — correct for infrastructure, where drift from the committed state is a defect. A development namespace inverts that assumption. It is poked at imperatively as a matter of routine: `devx <project> down` scales a project's containers to zero to reclaim node resources, containers get restarted, specs get edited live while something is being debugged. Under the platform's normal sync policy, scaling to zero would last only until the next reconcile, because git says `replicas: 1` and self-heal exists precisely to make live match git. Argo CD would spend the day undoing the workflow.

**Decision:** A **single** Argo CD `Application` for `k8s/apps/personal/workbench/` under the `personal` AppProject — one Application, not an ApplicationSet, because ADR-0054 produced exactly one namespace and there is nothing to generate over (unrelated to issue #42). `syncPolicy` is **manual**, with no `automated` block and no `selfHeal`. `ignoreDifferences` is set on `apps/Deployment` for `/spec/replicas`, so a scaled-to-zero project is not reported as drift and is not reverted. Secrets stay imperative and uncommitted, per the repo-wide constraint from ADR-0003. This adoption is deliberately the **last** milestone in the sequence: the shape gets to stop moving before it gets declared.

**Consequences:** The workspace's structure is reproducible from git — a rebuild recreates the namespace, the PVC, the devbox, and every project's Deployments and Services — while the *runtime* state of replica counts remains the operator's to set imperatively. The tradeoff is that a genuine, unintended replica drift is now invisible to Argo CD, which is the price of the exemption and acceptable in a namespace whose whole purpose is to be changed by hand. Manual sync also means a commit to `workbench` manifests does not take effect until someone syncs, which is correct here — the same "review the diff before it lands" caution ADR-0044 applied to adoptions, kept permanently rather than as a first-sync precaution.

## ADR-0062 — `homelab-k8s` and `homelab` are excluded from in-cluster development
**Status:** Accepted (planned — issue #59)

**Context:** The devbox is intended to hold every repo the operator works on, and the two infrastructure repositories are the ones worked on most. They are also the two that cannot safely be developed from inside the cluster they describe. A `terraform apply` run from a pod scheduled on `k3s-worker-1` is executing inside a VM that the same Terraform state manages — it can destroy or replace its own execution environment partway through the apply, killing the process mid-operation and leaving the state file locked with real infrastructure in a partially-applied condition. Ansible runs against the k3s nodes have a milder version of the same problem, and a `kubectl apply` that reconfigures the cluster can sever the very exec channel ADR-0056 depends on.

**Decision:** `homelab-k8s` and `homelab` are explicitly out of scope for this workflow. They are not checked out onto the workspace volume and are not developed from the devbox. Both stay on the MacBook, or on a Proxmox VM outside the k3s cluster — a control point whose lifecycle is not owned by the thing it is changing.

**Consequences:** The "all my code is on the devbox" property has two named exceptions, and they are the exceptions most likely to be forgotten in a hurry, which is why they are written down as a decision rather than left to memory. The Mac therefore keeps a working Terraform/Ansible/kubectl toolchain — it does not become a *pure* thin client, only a thin client for application development. This also means an infrastructure change that breaks the cluster does not simultaneously destroy the environment needed to fix it, which is the property being bought.

## ADR-0063 — No backups for the workspace volume; GitHub is the backup and the rule is commit before you stop
**Status:** Accepted (planned — issue #67)

**Context:** The workspace PVC is a single-replica Longhorn volume (ADR-0051, ADR-0055) holding 14 repositories, every dependency tree, and every build cache. Losing the node that holds that replica makes the entire development environment unavailable until the node returns; losing the replica itself loses whatever was not pushed. The platform's full backup strategy — off-box etcd snapshot shipping, Velero, Proxmox Backup Server — is still deliberately deferred (see `ROADMAP.md`), so there is no existing mechanism to opt this volume into, and building one for this volume specifically would be a real piece of work.

**Decision:** **No backups of the workspace volume, by decision.** The durable copy of everything that matters is GitHub, reached via the ADR-0056 transport, and the operational rule that makes that true is *commit before you stop* — the same rule ADR-0056 already imposes for a different reason (one side hot at a time). No second Longhorn replica, no Velero schedule, no snapshot job. This is recorded explicitly so it reads as a considered choice rather than an oversight found later during an incident.

**Consequences:** A node loss makes the workspace **unavailable**, not destroyed — the volume returns with the node, and RWO scheduling (ADR-0055) means no pod runs against it in the meantime. What is genuinely at risk is uncommitted work, bounded by however long ago the last commit was, which is exactly the exposure the operating rule is designed to keep small. Everything else on the volume is reconstructible by definition: repositories re-clone from GitHub, and `node_modules`/`.venv`/`GOMODCACHE` re-install from their lockfiles. Revisit if the workspace ever accumulates something that is neither committed nor reproducible — at which point the right fix is to stop keeping such a thing there, not to add a backup for it.

## ADR-0064 — Tailscale sidecar with `--ssh` for the devbox, not an operator-exposed Service on port 22
**Status:** Accepted (planned — issue #60)

**Context:** The devbox has to be reachable as an SSH host from the MacBook, because VS Code Remote-SSH is the mechanism that moves the language server off the laptop — the largest single battery win in this milestone. This platform already has two established ways to expose something over the tailnet (ADR-0018): the Tailscale Operator's `loadBalancerClass: tailscale` Service, and its `Ingress`. Either could put port 22 on the tailnet, but both presuppose there *is* a port 22 — meaning a real `sshd` inside the devbox, with host keys to generate and persist, an `authorized_keys` file to manage, and a second authentication system to keep correct alongside the tailnet's own. Tailscale SSH removes that entire layer: `tailscaled --ssh` terminates SSH itself, authenticating the connection against tailnet identity and authorizing it against the tailnet ACL, with no SSH daemon, no host key, and no key file in the pod at all.

**Decision:** The devbox pod runs a **Tailscale sidecar container with `--ssh`**, joining the tailnet as its own node, rather than exposing port 22 through an operator-managed Service. Access is granted by a `tag:devbox` ACL rule so it is one grant rather than a per-host entry, and the same tagging pattern extends to the per-frontend Tailscale `Ingress` nodes so the ACL stays a single rule regardless of how many dev frontends exist. The devbox image is **Debian-slim based, not Alpine** — VS Code Remote-SSH's server is dynamically linked against glibc and does not run on musl, so Alpine breaks the primary use case outright. Acceptance is `ssh workbench` working from the Mac, VS Code Remote-SSH attaching and installing its server into `$HOME`, that server surviving a pod restart (which is why `$HOME` is on the PVC, ADR-0055), and no language-server process running on the Mac during a normal session.

**Consequences:** No sshd, no host keys, no `authorized_keys`, and no credential material in the devbox image — authentication and authorization are both the tailnet's, managed in one place with everything else on it. The devbox appears as an ordinary tailnet node, so `ssh workbench` works from any authorized device without per-device setup. The base-image constraint is a real one and worth remembering: the natural instinct for a small dev image is Alpine, and choosing it here would silently break Remote-SSH in a way that looks like a networking problem. The accepted cost across this milestone is one tailnet node per exposed thing — the devbox plus one per exposed dev frontend — which the tag-based ACL keeps from turning into per-host policy sprawl.
