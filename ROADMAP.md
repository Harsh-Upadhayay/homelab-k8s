## v2.0 — Operability (in progress)
The platform grows the things that make it *operable*: storage, GitOps, observability, backups.
- [x] Distributed storage — Longhorn 1.12.0 live with one data copy per current volume by default; selected volumes can be promoted manually (ADR-0051 supersedes ADR-0030). Upstream `longhorn-system` remains conventional (ADR-0032), and the auth-less UI is internal-only at `longhorn.in.neovara.uk` (ADR-0033). The initial two Dell workers proved scheduling behavior but shared one physical USB SSD. Issue #48 retired the second Dell VM, consolidated its resources into `k3s-worker-1`, and converged storage onto one worker per physical host: a 650 GiB Dell virtual disk and a 1,300 GiB VM disk on ASRock's dedicated `longhorn-hdd` datastore.
- [x] Monitoring + logging — kube-prometheus-stack 87.10.1 (Prometheus, Alertmanager, Grafana, kube-state-metrics, node-exporter) + Loki 7.0.0 + Grafana Alloy 1.10.0, all in `monitoring`, all on the `longhorn` dev storage tier (ADR-0034). Grafana and Prometheus exposed internal-only via IngressRoute, same Tailscale-only pattern as Longhorn's UI; Grafana's own login removed entirely rather than left as an unused extra (ADR-0036). Loki wired into the same Grafana as a provisioned datasource — no second Grafana, no manual UI step (ADR-0037). Alloy runs as a single Deployment reading logs via the Kubernetes API, not the chart's default per-node DaemonSet, after catching that the default would have tripled log ingestion on this 3-node cluster (ADR-0038); Service names pinned via `fullnameOverride` so the whole stack rebuilds from Git with zero manual `kubectl get svc` steps (ADR-0035). Verified live: all Prometheus targets scraping (including node/pod/container metrics via cAdvisor and kubelet), logs flowing from all 8 active namespaces with no duplication, 27 dashboards + 3 datasources auto-provisioned. Caught two real chart-default bugs along the way — Loki's bundled chunks-cache defaulting to an unschedulable 8Gi, and a River-syntax comment (`#` instead of `//`) that crash-looped Alloy — neither of which `helm template` could catch on its own.
- [x] GitOps bootstrap — ArgoCD 10.1.2 (v3.4.4) live, self-managed via app-of-apps (ADR-0042), internal-only at `argocd.in.neovara.uk` (ADR-0043). Traefik migrated as the first GitOps-managed app, proof-of-concept for the rest (ADR-0044) — first sync diff was tracking-annotations only, confirming a clean adoption.
- [x] Complete the initial GitOps migration (issue #14, ADR-0046) — cert-manager, Longhorn, cloudflared, Loki, Alloy, and kube-prometheus-stack plus their hand-written companions moved under Argo CD. At that checkpoint all nine platform Applications were `Synced`/`Healthy`; Tailscale was the one intentionally deferred component. The later Tailscale adoption below supersedes only that exception. The migration also surfaced issue #28 (Loki PVC drifted to `local-path`, contradicting ADR-0034).
- [x] Tailscale Operator GitOps adoption — chart `1.98.4`, API-server RBAC, and monitoring `ProxyClass` are now managed by the `tailscale` Argo CD Application. The existing `operator-oauth` Secret remains imperative and untracked; omitting `oauth.*` from the values makes the chart consume that Secret without Argo CD owning or pruning it (ADR-0048).
- [x] Argo Rollouts (progressive delivery) — controller + CRDs + full-access dashboard onboarded GitOps-native (ADR-0045). The `whoami` exercise then proved Traefik-weighted canary routing and the committed blue/green active/preview flow, including live promotion; issue #26 is closed (ADR-0047).
- [x] Metrics scraping for existing infra + real dashboards (issue #25, closed) — Longhorn (`metrics.serviceMonitor.enabled: true`) and Traefik (`metrics.prometheus.service/serviceMonitor.enabled: true`) both wired up, plus k3s's control-plane components (kube-scheduler/kube-controller-manager/etcd), which needed a real k3s server config change — `bind-address=0.0.0.0` / `etcd-expose-metrics: true` via Ansible — and hand-authored `Endpoints` objects, since k3s runs these as threads inside its own binary rather than as pods a Service selector could ever match (ADR-0040). Along the way, found and fixed a bigger bug underneath all three: Prometheus's ServiceMonitor discovery was never actually cluster-wide by default, contrary to an assumption baked into the original monitoring install — `serviceMonitorSelectorNilUsesHelmValues` defaults to `true`, scoping discovery to the chart's own release label (ADR-0039). Official Grafana dashboards for Traefik (ID 17347) and Longhorn (ID 17626) were first imported via labeled ConfigMaps (ADR-0041), then consolidated into kube-prometheus-stack's chart-native `grafana.dashboards` values. Verified live at completion: all three control-plane jobs plus `traefik-metrics`/`longhorn-backend` showed `up`, and both dashboards were populated.
- [x] Physical-host expansion, Immich recovery, and worker/storage convergence — installed Proxmox on the workstation SSD, joined `pve-asrock` to the `neovara` cluster (ADR-0049), added `k3s-worker-3` through Terraform/Ansible, and reassociated the retained Immich replica by disk UUID. Database/path/playback/restart acceptance passed and obsolete bare-metal objects were removed (#38). The follow-on convergence evacuated and retired `k3s-worker-2`, enlarged `k3s-worker-1`, replaced the temporary raw-HDD recovery passthrough with a separate Proxmox-managed LVM-thin datastore, and placed the large one-copy volumes on ASRock (#48, ADR-0052). The existing control-plane VM move remains #49; a third Proxmox node still follows in one to two months.

## v4.0 — Developer Workspace
Development moves off the MacBook and into the cluster. The Mac becomes a thin client — no container runtime, no language server, no local builds — while a devbox pod holds the checkouts, the tooling, the dependency caches, and the test runs. Two Kubernetes facts did most of the design work: PVCs are namespaced, and containerd reads images only from its own per-node content store (ADR-0054, ADR-0059).
- [x] M0 — Workbench groundwork (issue #59): a single flat `workbench` namespace holding the devbox plus every project's app containers, chosen over per-project namespaces because a namespaced PVC would otherwise force either a devbox per project or a shared RWX volume (ADR-0054). One RWO Longhorn PVC for `/workspace` and `$HOME`, with Longhorn 1.12's RWX rejected on daily small-file performance — it is NFSv4 underneath and `node_modules`/`.git`/build caches are the worst case for it — not on capability (ADR-0055). A dedicated StorageClass with `dataLocality: best-effort` rather than either existing class — both already allow expansion, so the originally-stated criterion did not discriminate, and both leave a single-replica volume free to sit on a different node from its pod, paying the same per-operation network tax RWX was rejected for (ADR-0055 amendment). Debian-slim devbox image (not Alpine — VS Code Remote-SSH needs glibc); project-prefixed service names, since a flat namespace has no other separation. The originally-planned per-project port-block table is dropped: a port lives in a network namespace and in Kubernetes the *pod* is that namespace, so a flat namespace never caused port collisions and per-project namespaces would not have prevented any. What replaces it is a lookup table of one stable dev port per project — for `devx` and M4's `targetPort`, not for collision avoidance — filled in as projects are onboarded (ADR-0054 amendment). `homelab-k8s` and `homelab` are excluded from the whole workflow: a `terraform apply` from a pod on the cluster it provisions can destroy its own execution environment mid-apply and leave state locked (ADR-0062).
- [x] M1 — Devbox pod with Tailscale SSH and VS Code Remote-SSH (issue #60): real Tailscale SSH rather than an operator-exposed Service on port 22 — ACL-gated via `tag:devbox`, no sshd, no host keys, no `authorized_keys` (ADR-0064). Run **inside the devbox container, not the sidecar originally specified**: Tailscale SSH spawns the login shell in the filesystem of whichever container runs `tailscaled`, so a sidecar would land you in the Alpine Tailscale image with no workspace and no glibc for Remote-SSH's server. Supervised by a `livenessProbe` instead of a separate container, in userspace networking with **no `NET_ADMIN` and no root**, and with `--statedir` on the PVC so the node identity survives restarts — verified resuming with no auth key after a full pod delete. The devbox's own Kubernetes access is namespace-admin on `workbench` only, via a `RoleBinding` referencing the built-in `admin` `ClusterRole` (ADR-0065), verified with the ServiceAccount's real token rather than `kubectl auth can-i --as`, which reports the caller's permissions when the caller is cluster-admin. This is the phase that moves the language server off the laptop; `$HOME` lives on the PVC so VS Code's server survives a pod restart. No Makefile target vocabulary — commands run directly in the shell, since the abstraction only ever existed to serve a remote-exec transport that SSH made unnecessary (ADR-0057).
- [x] ~~M2 — Credential-free git transport (issue #61)~~ — **skipped, not planned.** M1's Tailscale SSH agent forwarding already delivers the credential-free property from the other direction: the Mac holds the GitHub key, the forwarded agent delegates its *use* for the session, and `~/.ssh/` on the PVC holds only `known_hosts` (verified). The exec transport would still have added an offline Mac↔pod path with no GitHub round trip, but at a standing discipline cost (one side hot at a time, commit before switching). A better file-sync approach will be revisited later. Original design: `git remote add pod "ext::kubectl exec -i ..."` against `deploy/devbox`, with `receive.denyCurrentBranch=updateInstead` on the pod side. The Mac holds the GitHub credential; the cluster holds none and cannot pull, push, or enumerate an org even if the devbox is compromised (ADR-0056). Costs a discipline rule — one side hot at a time, commit before switching — and `updateInstead` rejecting a push into a dirty tree is the safety rail, not a bug.
- [x] M3 — `devx` CLI (issue #62): one command from a cold cluster to a working shell — scale a project's containers up, `kubectl wait --for=condition=available`, then SSH in; `devx <project> down` scales back to zero. The devbox itself and long-lived Postgres stay running, since cold-starting a database mid-thought is the most disruptive possible interruption. Shipped at `bin/devx` and symlinked onto `PATH`, not a stray script in `~/bin`. Workloads are discovered entirely by label — `workbench.neovara/project` plus `workbench.neovara/lifecycle: always-on|on-demand` — so adding one is a label on its Deployment and nothing else, and the same selectors work from plain `kubectl` (ADR-0066). Cluster-unreachable is handled as a supported offline mode rather than a raw `kubectl` timeout. Two items from the original sketch were dropped as stale: the per-project port block (eliminated by the ADR-0054 amendment) and `devx pull` as a `git fetch pod` against the exec transport that #61 skipped. Bash, not Go, until the shape settles — and portable to macOS's bash 3.2, which has no `mapfile`.
- [x] M4 — Dev frontend exposure (issue #63): built as Cloudflare Tunnel + Traefik `IngressRoute`, not the originally-planned per-frontend Tailscale `Ingress` (ADR-0054 amendment) — a wider pattern was already live for eight platform/admin UIs (`argocd`, `longhorn`, `grafana`, `prometheus`, Traefik's own dashboard, `immich`, `whoami`, `argo-rollouts`) via `*.in.neovara.uk` → the same public tunnel → Traefik's `websecure` entrypoint, gated by Cloudflare Access rather than tailnet membership. Reusing it keeps one exposure mechanism cluster-wide instead of two. Each dev frontend gets an `IngressRoute`+`Middleware` in its own repo, next to its dev `Deployment`/`Service` — same shape as every other internal route. Dev names avoid live workloads (`kiroku-dev.in.neovara.uk`, since `kiroku` already runs in-cluster). One easy-to-lose requirement found live: the `IngressRoute` needs an explicit `tls: {}` on `websecure`, or it silently registers as plain HTTP and 404s everything while the pods stay healthy.
- [x] M5 — Multi-container inner loop on `kiroku` (issue #64): both containers mount source from the same PVC as the devbox (`subPath: kiroku`, `subPath: kiroku/backend`) and run their own dev servers, verified live with an actual round-trip — editing `index.html` on the devbox changed the served page on the next request, same pod, no restart. Dependency directories live on the volume too (`node_modules` via `npm install` from the devbox — **not** baked into the dev image, since the source mount would shadow it anyway; `go mod download`'s `/go/pkg/mod` sits outside the mounted path so it isn't shadowed and stays in the image). Real bugs only found by running it: `NODE_ENV`/`imagePullPolicy` copy-paste carryovers from prod; the backend's exec healthcheck referencing a compiled binary that only exists in the *prod* image, not the `go run` dev one; `KIROKU_API_URL` needed explicitly in dev because prod's `IngressRoute` peels `/api` off before the frontend's built-in proxy ever runs, making that proxy dead code there; Vite's `allowedHosts` rejecting the `.in.neovara.uk` Host header. No file watcher on the Go side — pick up backend edits with `kubectl rollout restart deploy/kiroku-api`.
- [x] M6 — In-cluster registry and BuildKit builder (issue #65): `registry:2` on a Longhorn PVC plus `buildkitd`, with builds run from the devbox where the source already lives. A registry is mandatory rather than optional because a Deployment cannot reference an image on a PVC — containerd reads only its own per-node content store — and `registry:2` beats ghcr.io on two counts: no external credential anywhere in the cluster, and no work-derived artifacts on a personal GitHub account (ADR-0059). Cost is `/etc/rancher/k3s/registries.yaml` trust config on all three nodes via Ansible. Scope is **dev only** — this builder must never feed Argo CD, since an in-cluster build path under GitOps produces artifacts not reproducible from git; real images come from CI (issue #27, ADR-0060).
- [x] M7 — GitOps adoption (issue #66): a single `workbench` Argo `Application` for top-level `k8s/workbench/manifests/` under the `default` AppProject — treated as a platform component beside Longhorn and Traefik, not as an app, since the `personal` project fences *external* dev-owned repos and workbench has none (ADR-0061 amendment) — not an ApplicationSet, since there is one namespace — with **manual** sync, no `selfHeal`, and `ignoreDifferences` on `/spec/replicas` so `devx <project> down` isn't reverted within minutes by self-heal (ADR-0061). Deliberately last: the shape should stop moving before it gets declared. Secrets stay imperative and uncommitted, per ADR-0003. **The Application adopts the namespace INFRASTRUCTURE only** — per-project dev Deployments, Services, and Tailscale `Ingress` objects are written in each project's own repo and applied with `kubectl` from the devbox, deliberately outside GitOps, because `workbench` is the operator's working environment rather than a deployment target (ADR-0061 amendment). That makes `prune` unsafe to arm, and it is left off; no label scoping is needed, because Argo compares git against objects carrying its own tracking-id marker rather than against the namespace contents — verified live.
- [x] M8 — ADR log, runbook, and roadmap (issue #67): `docs/adr/v4.0 - Developer Workspace.md` (ADR-0054 … ADR-0064) plus `docs/Workbench Runbook.md` covering the daily loop, the offline flip, the port-block table, and recovery when the PVC's node is down. Includes the decision to run **no backups** for the workspace volume — single-replica means a node loss makes it unavailable until the node returns, GitHub is the real backup, and the rule is commit before you stop; recorded as a choice, not an oversight (ADR-0063).

## Deferred — deliberate, not forgotten

These are the remaining deliberate follow-ons. None are missing by accident; see `claude.md` for the current constraints and exceptions.

- **Secrets management** (SOPS + age, later External Secrets Operator + Vault) — Kubernetes Secrets stay imperative and uncommitted until this lands.
- **Full backup strategy** — off-box etcd snapshot shipping (`--etcd-s3-*`), Velero, Proxmox Backup Server. Local etcd snapshots are already running from Phase 5.
- **Cilium** — the one *non-additive* item on this list. Flannel → Cilium is a full cluster rebuild, not a live migration; treated as its own dedicated project and a real rebuild-from-Git/DR drill.
- **HA k3s control plane** (`k3s-server-2`, `k3s-server-3`) and **additional workers beyond `k3s-worker-3`** — separate from the completed Proxmox/Immich expansion. Exactly two embedded-etcd servers are not HA; real k3s HA uses three. Each host/VM still belongs in Terraform and Ansible before it joins.
